# ROADMAP — Қақпан (Qaqpan)

> План по фазам. Каждая фаза заканчивается gate. Код — только после Gate 0.
> Версия: 1.0 (2026-11-13).

## Две основные функции проекта

1. **Бот-ловушка:** ведёт диалог с предполагаемым мошенником, пытается получить реквизиты, на которые тот просит перевести деньги, и передаёт их вместе с контекстом аналитику для проверки.
2. **Защита клиентов от обмана:** оценивает перевод, задаёт уточняющий вопрос и при высоком риске подключает доверенное лицо; поддерживает тайм-аут и отмену.

Это объединённая идея, а не альтернативные проекты. **Синтетический «мошенник-робот» из Phase 4 — инструмент тестирования защиты, а не бот-ловушка.** Бот-ловушка пока не реализован; его план приведён в отдельном блоке ниже. Уже выполненная работа над защитой переводов сохраняется.

## Принципы

- Контракты → моки → параллельная работа бэка и фронта → интеграция → бенчмарк → полировка.
- Один шаг = один проверяемый результат.
- Фронтендер никогда не ждёт бэкенд: с первого дня работает по мокам.
- Если не влезаем — резать фичи робота-мошенника, но не трогать FSM, 3 экрана и демо-сценарий.

## Оставшиеся работы и ограничения проверки

- Тесты теперь идут на временной SQLite (`backend/tests/conftest.py`); реальная БД не затрагивается. Таймеры и «привычная сумма» настраиваются через `TRUSTED_TIMEOUT_SECONDS` / `CLIENT_TYPICAL_AMOUNT` (`backend/app/config.py`).
- Test-сплит дополнен 30 «трудными» законными сценариями (`benign_hard`), train — 12 такими же (другие тексты). Первый прогон test выявил 6 ложных срабатываний на словах «инвестиции», «адвокат/заңгер», «полиция». Исправлено по общим соображениям, не подгонкой под test: «обычные» слова (полиция, адвокат, заңгер…) считаются давлением только вместе с указанием/срочностью/страхом, «инвестиции/крипто/брокер» — только рядом с приманкой (гарантия, дивиденды, табыс, пайда…); потеря recall на train восстановлена за счёт приманок на KZ/RU. Итог: train Stop 94.3% / FPR 1.1%; test Stop 100% / FPR 16% (как у baseline, остаток — крупные суммы новым получателям). Test теперь «просмотрен» при ревью — для финальных цифр нужен свежий test-набор.

- Добавлено `POST /api/v1/analyst/transfers/{id}/review` (`decision: APPROVE|DECLINE`): MANUAL_BANK_REVIEW → COMPLETED/BLOCKED, без авторизации (закрытое тестовое окружение). Валидация создания перевода ужесточена (непустые поля, сумма ≤ 1 млрд, язык ru|kz); `CORS_ORIGINS` из `.env` учитывается (по умолчанию `*`).
- «Привычная сумма» теперь считается по клиенту: медиана его последних завершённых LOW-переводов (от 3 штук, иначе `CLIENT_TYPICAL_AMOUNT`); завершённые HIGH/MEDIUM не учитываются. Доверенное лицо можно передать при создании перевода (`trusted_contact_name/phone`), иначе демо-контакт. Вопрос без ответа дольше `ANSWER_TIMEOUT_SECONDS` (300 с) отменяет перевод при попытке ответа (409, проверка ленивая, фонового таймера нет).
- Период охлаждения: после молчания близкого клиент сразу может отменить перевод или запросить проверку банка, но подтвердить сам (`/confirm`) — только через `COOLING_PERIOD_SECONDS` (30 с в демо; 409 с остатком секунд до конца). В ответе перевода поле `cooling_seconds_left` для таймера на экране.
- Аккаунты, роли и защищённое решение сотрудника банка отложены до завершения основных частей Frontend, Backend 1 и Backend 2. До этого не заявляем готовность к внедрению.
- Проверки PostgreSQL 18.7 выполнялись в отдельной временной схеме; рабочие таблицы не затронуты, тестовая схема удалена. Для проверки правил использовался offline fallback, внешние LLM-вызовы не выполнялись.
- Сохранить расширенные проверки гонок и восстановления таймеров в репозитории после согласования зоны `backend/tests/` с Backend 3. Сейчас они находятся во временных скриптах, а не в штатном наборе тестов.
- Проверить интеграцию с готовым фронтендом: формы, предупреждения, статусы и синхронизацию трёх экранов. До этого общие gates не закрыты.
